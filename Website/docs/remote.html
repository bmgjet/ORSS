Remote control and serial commands

Every byte a skeleton ROM understands on its datalog cable, and how to build your own remote control panel — a phone, a tablet or a box of buttons — that switches the fan, sets limits, unlocks the engine and more.

What you need in the ROM

The commands live in modules of a skeleton ROM. Tick the ones you want when you create it (or later, with Change functions):

ModuleWhat it adds
Datalogging: HTS / ISR frameThe serial link itself (every other module here needs it) and the 51-byte frame existing loggers read.
Datalogging: channel streamThe app's fast datalog: only the channels you ask for.
Datalog service commandsClear codes, injectors off, timing locked, maps chosen, GIO outputs forced on.
Serial inputsValues sent to the ECU, used as extra sensor or switch inputs.
Memory readAny 32 bytes of the ECU's RAM, read while it runs.
Remote control commandsFan on/off, rev and speed limits, the boost cut, VTEC point, shift light, launch rpm, limiter cut type and rolling idle set, popcorn mode, an anti-start lock with a main and a guest (valet) password.

The remote control commands are off until enabled: tick Take the remote control commands on the ROM's Added features > Serial port page. Until then every one of them is answered 7Fh and nothing changes. The same page holds the lock, the two passwords, valet mode's limits and popcorn mode's settings.

Forgotten at key-onEverything set over the cable — a rev limit, the fan forced, popcorn on, a boost cut — lasts until the ECU is switched off. At the next key-on the ROM runs exactly as calibrated (and locked again, when the anti-start lock is on). A panel that wants a setting kept sends it again after each start.

The line

  • 38400 baud, 8 data bits, no parity, 1 stop bit (62500 when the ROM has 62,500 baud on, Serial port page), on the ECU's datalog transmit and receive pins — the same wiring a datalog cable uses. Logic level serial: a USB-serial adapter, a Bluetooth serial module or a microcontroller's UART, with a common ground.
  • One byte at a time. The ECU has a one-byte receive buffer: leave about 1 ms between bytes of a command (the value bytes after 2Ch, 33h, 35h, 2Fh).
  • Every command is answered with one byte, normally within a few milliseconds. Wait for it (allow 200 ms) before sending the next command. 7Fh means "this ROM cannot": the module is not built in, not enabled, or (after a password) the password was wrong.
  • Only one talker. The ECU has one receive line: a laptop logging and a panel cannot both send at the same time. A panel can be the logger as well, or the laptop can send the commands for you (Codes and service).

While the channel stream is running

The channel stream (71h) sends frames back to back until any other byte arrives. To send a command in the middle of a log:

  1. send 00h (a byte the ROM ignores): the stream stops after the frame it is sending;
  2. wait about 30 ms and throw away what has arrived;
  3. send the command and read its answer;
  4. send 71h to start the stream again.

Serial inputs (FFh, input, value) are the exception: they do not stop the stream and get no answer.

Anti-start lock: main and guest passwords

With No password, no start ticked, every key-on starts locked: the engine cranks but gets no fuel and no spark until a password is sent. Tick No or a wrong password: valet mode instead of no start as well and it starts anyway, held to valet mode, until the main password is sent. There are two passwords:

  • The main password runs the engine as tuned.
  • The guest password (when Take the guest password is ticked) runs it in valet mode: its own rev limit, speed limit and softer timing, set on the same page — 4000 rpm, 60 km/h and 4° less by default.

Each password is a number from 0 to 65535 (two bytes, as a ushort), sent high byte first: 1234 is 04D2h, so send 2Fh 04h D2h; 12345 is 3039h: 2Fh 30h 39h; 65535 is 2Fh FFh FFh. Keep the two different. A rev or speed limit sent with 33h / 35h wins over valet mode's. Sending the main password while in valet mode puts the engine back as tuned; the guest password works with the lock off too, to switch valet mode on.

Not a security systemAnyone with a laptop and this page can send passwords; the ECU can be swapped. It stops a casual start, a valet or a learner — like a hidden switch — and is as strong as your password and your wiring.

Popcorn mode

Off the throttle above its rpm (Serial port page: Works above, With the throttle at or under), the ROM keeps the fuel on instead of the overrun cut, adds fuel, takes timing out and cuts the sparks every other tick, so fuel burns in the exhaust and pops. Back on the throttle, or below the rpm, everything is normal again. Above the ROM's own rev limit the fuel cut always wins.

Hard on partsPopcorn mode heats the exhaust, the catalytic converter (it will not survive long) and the turbo. Use it for short spells.

Serial inputs make a panel's switches into ECU inputs too: a button that sends FFh 05h 01h while held (and FFh 05h 00h when let go), with input 5 kept as serial input 1, can be the launch control or speed limiter switch — pick serial input 1 in that module's input list.

Building a remote control panel

Any device that can send bytes at 38400 baud will do. Three common ways:

  • A phone or tablet with a Bluetooth serial module (an HC-05 or similar, set to 38400 baud) wired to the datalog pins: a serial terminal app with buttons, or your own app.
  • A microcontroller (Arduino, ESP32) with real buttons and an LCD, its UART on the datalog pins.
  • A small computer (a Raspberry Pi, a laptop) with a USB-serial adapter: a script or a web page served on the car's Wi-Fi.

Wiring: the device's TX to the ECU's datalog receive, its RX to the ECU's datalog transmit, ground to ground. Power the device from a switched 12 V supply through a proper 5 V regulator, not from the ECU.

The pattern every panel follows

  1. At start (and every few seconds): send 3Fh. No answer: the ECU is off. 7Fh: the remote commands are not enabled. Otherwise show the state — locked, valet mode, fan and popcorn.
  2. When locked: ask for the password and send 2Fh hi lo. Show "wrong password" on 7Fh.
  3. A button press: send its command, wait for the answer, then send 3Fh (or 34h / 36h / 38h / 3Ah) to show what the ECU now has. Show what the ECU says, not what the button was meant to do.
  4. After the ECU restarts (no answer for a while, then answers again), send again whatever the panel wants kept.

Example: a Python script (a laptop or a Raspberry Pi)

import serial, time

ecu = serial.Serial("COM5", 38400, timeout=0.2)   # /dev/ttyUSB0 on Linux

def command(*data):
    """Send one command (and its value bytes), return the ECU's one-byte answer or None."""
    ecu.reset_input_buffer()
    for b in data:
        ecu.write(bytes([b]))
        time.sleep(0.002)                  # the ECU takes one byte at a time
    answer = ecu.read(1)
    return answer[0] if answer else None

state = command(0x3F)
if state is None:
    print("no answer: is the ECU on?")
elif state == 0x7F:
    print("remote commands not enabled in this ROM")
else:
    if state & 0x40:                      # locked
        pw = 1234
        r = command(0x2F, pw >> 8, pw & 0xFF)
        print("wrong password" if r == 0x7F else "unlocked, valet mode" if r == 0x81 else "unlocked")
    command(0x31)                          # fan on
    command(0x33, 4000 // 50)              # rev limit 4000 rpm
    print("rev limit now", command(0x34) * 50, "rpm")
    command(0x39, 0xD0)                    # VTEC at 5000 rpm (the rpm byte)
    command(0x2D)                          # all back to normal

Example: an Arduino with three buttons

// Buttons on pins 2, 3, 4 to ground: fan on, fan auto, popcorn toggle. Serial1 on the datalog pins.
const byte FAN_ON = 0x31, FAN_AUTO = 0x30, POP_ON = 0x3D, POP_OFF = 0x3E, STATE = 0x3F;
bool popcorn = false;

int command(byte c) {                      // one command, its answer (-1: none)
  while (Serial1.available()) Serial1.read();
  Serial1.write(c);
  unsigned long t = millis();
  while (!Serial1.available()) if (millis() - t > 200) return -1;
  return Serial1.read();
}

void setup() {
  Serial1.begin(38400);
  for (byte p = 2; p <= 4; p++) pinMode(p, INPUT_PULLUP);
}

void loop() {
  if (digitalRead(2) == LOW) command(FAN_ON);
  if (digitalRead(3) == LOW) command(FAN_AUTO);
  if (digitalRead(4) == LOW) {
    int s = command(popcorn ? POP_OFF : POP_ON);
    if (s != -1 && s != 0x7F) popcorn = !popcorn;
  }
  int st = command(STATE);                 // keep the panel's idea in step with the ECU
  if (st >= 0x80 && st != 0x7F) popcorn = st & 0x04;
  delay(250);                              // a crude debounce, and a gentle poll
}

Trying it without a car

Open the ROM in Rom Sim Studio, start the simulator and connect the datalog to it (Datalogging menu). Datalogging > Codes and service has a Remote control section with every command as a button — fan, popcorn, and the rev limit, speed limit, boost cut and VTEC point each typed in your units with Set, Clear and Read (all read when the window opens), password and lock — and shows what the ECU answers, so a panel's behaviour can be checked before it goes in a car. The Limiters cutting channel shows remote (its limits and the lock) and popcorn while they cut.
