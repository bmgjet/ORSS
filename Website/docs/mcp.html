MCP server and command line

Let an AI agent — or a script — assemble, run, explore, calibrate and datalog ROMs.

The MCP server

The Model Context Protocol lets an AI agent (Claude and others) use the program's tools. Two ways:

Start itWorks on
Settings > MCP server: tick Run the HTTP MCP server while the app is openThe ROM open on screen. The agent's edits go through undo, the safe limits and the checksum, reach the simulator, and the emulator if it is uploading — you watch them happen.
RomSimStudio --mcp --root <folder> [--read-only]Files in a folder, over stdio, with no window.

The HTTP server listens on 127.0.0.1 and the port set there, and asks for the password set there (Authorization: Bearer …). Allow remote connections listens on the network too; Read-only lets clients read and run, not write. The settings page shows the configuration to paste into a client.

Only programs on your computer are answered: a request that names another website as its origin, or a host name that is not this machine's, is refused, so a page open in your browser cannot use the server even with no password set. Five wrong passwords lock an address out for five minutes (counting starts again after that). A file path a client gives must stay inside the workspace, including through folder links and junctions.

The tools cover the instruction set, assembling and disassembling, running the simulator with inputs, symbols and cross-references, finding every map, comparing two ROMs, the whole calibration surface (list, read, write, define, detect, formulas, feature patches, save as .bin / definitions / XDF), the datalog, the emulator, and the files in the workspace. Every call is in the Debug tab with where it came from and how long it took.

Annotating a ROM with a model

A model connected to the server can name a ROM by following its code — a local one such as Qwen as well as Claude. With the ROM open in the app, everything it changes shows as it is made: the source in the editor (the caret and scroll stay where you left them), the names in the disassembly, Lookup & breakpoints and the call stack, and the Calibration pages — without a reset, the simulator carrying on. A change that would break the build is reported back to the model with the errors, and the Build button lights so you can see it.

Every name follows one standard, so a ROM named by different models, or over many sessions, reads as one. The model reads it with naming_guide; rename refuses a name that breaks it:

WhatStyleExamples
Code labelslower_snake_case, the first word the part of the ECU (fuel, ign, idle, vtec, crank, knock, dtc, serial…), then what it doesfuel_calc_base_pulse, ign_apply_knock_retard, fuel_calc_base_pulse_done
Calibration dataPascalCase; tables end in Tbl, switches in EnableCrankingFuelTbl, RevLimitLow, O2HeaterEnable
RAMlower_snake_case after the value kept thererpm_period, ect_filtered, knock_retard_now
ConstantsUPPER_SNAKE_CASEMAP_COLS

Names a disassembler or an earlier pass made up — loc_1234, tbl_5e20, an address or a number in the name, an echoed instruction like int_serial_rx_load_r7_2 — count as placeholders still to be named. The tools for the job:

ToolDoes
naming_guideThe standard, the comment style and the workflow.
annotate_todoWhat is still unnamed, most-used first, and how far the ROM is named (a percentage).
explore, xrefFollow a routine and what it reads, writes, calls and drives; every instruction that uses an address, branches included.
renameA new name everywhere it is used, in every source file of the build, checked against the standard.
commentA comment block above a routine, or a comment on one line.
name_checkWhether a name follows the standard, and what to change.
cal_defineName a table or setting found in the code, with its type, scaling, unit and category: it appears on the Calibration pages.

A good first message for the model: "Read naming_guide, then annotate the ROM open in the app: take annotate_todo's first entries, explore each, rename it and comment it. Only name what the code shows." Its file_edit and file_write calls on the ROM's own files go through the app the same way.

The command line

okisim does the same from a terminal:

okisim asm file.asm [-o out.bin] [-D NAME=val] [-I dir] [--lst --map --sym]
okisim run file.bin|file.asm [--steps N] [--until label] [--trace N] [--rpm N] [--watch label]
okisim disasm file.bin [--from 2528] [--count 40] [--sym file.sym]
okisim symbols <rom> [pattern] [--at ADDR]
okisim xref <rom> <addr> [--max N]
okisim defs <rom> [--defs f.okidef.json] [--filter text] [--category name]
okisim get <rom> <name|label|address> [--type u8] [--formula name]
okisim set <rom> <name|address> <value> [--cell R,C] [--all] [--add X] [--scale X] [--raw]
okisim formulas [name]
okisim features <rom> [--apply id,id] [--remove id] [-o out.bin]

set is held to the same safe limits as the editor, and keeps the checksum right.
